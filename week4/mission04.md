# 폴더 구조 알아보기

## 주요 폴더의 역할 알아보기

### `components/`: 화면을 이루는 부품을 제공하는 역할 (초급~)
- 버튼, 모달, 카드처럼 **여러 곳에서 쓰는 UI 조각**을 책임진다.
- 초급에서는 모든 컴포넌트를 여기에 넣지만, 컴포넌트가 15개 정도를 넘으면 관리가 어려워진다.
- 중급부터는 **여러 페이지에서 쓰는 전역 컴포넌트만** 두고, `ui/`(버튼, 모달, 카드), `form/`(체크박스, 입력칸, 날짜 선택) 처럼 하위 폴더로 나눈다.
- 따로 두는 이유: 같은 UI를 **한 번 만들어 여러 번** 쓰기 위해서.

### `hooks/`: 커스텀 Hook을 모아 두는 역할 (초급~)
- **커스텀 Hook**을 책임진다. 글은 이 폴더가 프로젝트 규모와 상관없이 유용하다고 한다.
- 중급부터는 **여러 페이지에서 같이 쓰는 Hook만** 두고, 한 페이지에서만 쓰는 Hook은 그 페이지 폴더로 옮긴다.
- 따로 두는 이유: 상태 로직을 컴포넌트에서 떼어 내 **재사용**하기 위해서.

### `pages/`: 화면 단위로 코드를 묶는 역할 (중급~)
- **페이지 하나에 필요한 것을 한 폴더에** 모은다. 각 페이지 폴더에 `index` 파일과, **그 페이지에서만 쓰는** 컴포넌트와 Hook을 함께 둔다. (예: `login/` 안에 `LoginForm`, `useLogin`)
- 고급 구조에서는 로직을 `features/`로 옮기고, `pages/`에는 **페이지당 파일 하나**만 얇게 남긴다.
- 따로 두는 이유: 전역 코드와 페이지 전용 코드를 나눠서, 한 페이지에 관련된 것을 **한 곳에서** 찾기 위해서.

### `assets/`: 코드가 아닌 파일을 보관하는 역할 (중급~)
- 이미지, CSS, 폰트처럼 **코드가 아닌 파일**을 책임진다.
- 초급 구조에는 정해진 자리가 없어서 `src` 바로 아래에 흩어지기 쉽다.
- 따로 두는 이유: 코드 파일과 섞이지 않게 하기 위해서.

### `context/`: 전역 상태를 담는 역할 (중급~)
- **React Context 파일**을 책임진다.
- Redux 같은 상태 관리 라이브러리를 쓰면 이 폴더를 그 **스토어 폴더로 대신**할 수 있다.
- 따로 두는 이유: 여러 컴포넌트가 함께 쓰는 상태를 **한 곳에서 관리**하기 위해서.

### `data/`: 데이터와 상수를 보관하는 역할 (중급~)
- **JSON 데이터, 상수, 설정값**처럼 코드에서 가져다 쓰는 고정된 값을 책임진다.
- 따로 두는 이유: 같은 값이 여러 파일에 흩어지지 않게 **한 곳에 모으기** 위해서.

### `utils/`: 공통 도우미 함수를 모아 두는 역할 (중급~)
- 날짜나 숫자 포맷 같은 **도우미 함수**를 책임진다.
- 글쓴이는 이 폴더에 **순수 함수**를 두는 것을 선호한다.
- 따로 두는 이유: 같은 계산을 **한 곳에 모으고**, 화면 코드와 섞이지 않게 하기 위해서.

### `features/`: 기능 단위로 코드를 묶는 역할 (고급)
- **장바구니, 로그인 같은 기능 하나에 필요한 모든 코드**를 책임진다. 각 기능 폴더 안에 `src`처럼 `components/`, `hooks/`, `context/` 등을 다시 둔다.
- 각 기능에는 `index` 파일을 두고, 밖에서는 **이 파일로만** 가져다 쓰게 한다(기능의 공개 창구).
- 글은 ESLint 규칙(`no-restricted-imports`)과 경로 별칭(alias)으로 이 규칙을 강제하는 방법도 소개한다.
- 따로 두는 이유: 기능을 추가하거나 고칠 때 **그 기능 폴더만** 보면 되게 하기 위해서.

### `layouts/`: 페이지 공통 틀을 담당하는 역할 (고급)
- 사이드바, 내비게이션 바, 컨테이너처럼 **여러 페이지가 같이 쓰는 바깥 구조**를 책임진다.
- 따로 두는 이유: 틀을 바꿀 때 **한 곳만** 고치기 위해서.

### `lib/`: 외부 라이브러리를 감싸는 역할 (고급)
- axios 같은 **외부 라이브러리를 한 번 감싼 코드(퍼사드)**를 책임진다.
- 따로 두는 이유: 나중에 라이브러리를 바꾸게 되어도 **이 폴더만** 고치면 되게 하기 위해서.

### `services/` (= `apis/`): 서버와 통신하는 역할 (고급)
- **외부 API 호출**을 모두 책임진다.
- 따로 두는 이유: 컴포넌트는 함수만 부르고, 주소나 요청 방법이 바뀌어도 **이 폴더만** 고치면 되게 하기 위해서.

### 테스트 파일
- 초급에서는 `tests/` 폴더 하나에 모으지만, 중급부터는 **테스트할 코드 바로 옆에** 둔다.

## 파일을 어떤 기준으로 분리하면 좋을지 정리하기

### 폴더 구조가 발전하는 단계

[참고 링크 및 구조도 확인](https://joong-sunny.github.io/react/react7/)

**LV.0 가장 단순한 구조**
- CRA로 처음 만들었을 때의 기본 구조.
- 실제 서비스가 이 모양인 경우는 거의 없다.

**LV.1 페이지와 레이아웃으로 나누기**
- 화면마다 `page`, 여러 화면이 같이 쓰는 틀은 `layout`으로 나눈다. (Next.js와 비슷한 방식)

**LV.2 복잡해진 구조**
- 대부분의 프로젝트가 결국 여기에 도달한다.
- 공용 컴포넌트, 디자인 시스템(버튼 등 UI), 서비스(API), 테스트, utils, 폰트, 색상 폴더가 생긴다.
- **문제점:** 하나의 대상(예: todo)과 관련된 코드가 **여러 폴더에 흩어진다.** 그래서 읽기 어렵고, 관심사가 잘 분리되지 않는다.

**LV.3 기능(Feature) 기준으로 나누기**
- 기능마다 폴더를 만들고, 그 기능에서만 쓰는 `hook`, `type`, `test`, `component`를 **기능 폴더 안에 같이** 둔다.

**LV.3-1 FSD (Feature-Sliced Design)**
- `app` → `page` → `UI` → `features` → `entities` → `shared` 순서로 레이어를 나눈다. 
- **위 레이어는 아래 레이어만** 가져다 쓸 수 있고, 반대는 안 된다.
- 공개된 FSD 예시들도 일부 레이어를 생략하고 쓰므로, 프로젝트에 맞게 골라 쓰면 된다.

**LV.3-2 FSD 변형**
- `page & layout` + 기능 폴더 구조를 유지하고, 여러 곳에서 쓰는 hook과 utils는 `shared`에 두거나 도메인별로 나눈다.
- 전체 구조를 크게 바꾸고 싶지 않은 팀에게 현실적인 선택이다.

**LV.4 모노레포**
- 프로젝트가 매우 커지면 저장소나 패키지 단위로 나눈다. (예: Supabase)

---

### 분리 기준

**1. 얼마나 넓게 쓰이는가**
- **여러 곳에서 쓰는 것**(공용 유틸, 공용 컴포넌트) → **상위(공통) 폴더**에 둔다.
- **한 기능에서만 쓰는 것** → **그 기능 폴더 안**에 둔다.

**2. 같은 대상의 코드는 가까이 (관심사의 분리)**
- 하나의 대상과 관련된 컴포넌트, hook, 타입, 테스트는 **흩어지지 않게 한곳에** 모은다.
- LV.2의 문제(코드가 여러 폴더에 흩어짐)를 해결하는 기준이다.

**3. 함께 쓰는 파일은 나란히 (Colocation)**
- `Card.jsx`와 그 테스트, 스토리 파일처럼 **같이 바뀌는 파일은 바로 옆에** 둔다. 
- 비교적 쉬운 부분이라고 한다. 

**4. 애매하면 팀이 합의한 곳에**
- 공통인지 기능 전용인지 애매한 코드는 **팀이 정한 규칙**을 따르면 된다. 중요한 건 **읽기 쉬운 상태를 유지**하는 것이다.

**5. 작은 기능은 굳이 폴더로 나누지 않기**
- 파일 한두 개짜리 작은 기능까지 폴더를 만들면 오히려 복잡해진다.

**6. 프로젝트 규모에 맞추기**
- 처음부터 FSD 같은 복잡한 구조를 쓰기보다, **지금 겪는 불편함**(코드가 흩어진다, 여러 페이지가 같은 기능을 쓴다 등)이 생길 때 다음 단계로 옮겨 간다.

---

### 정리

| 기준 | 질문 | 결정 |
|---|---|---|
| 사용 범위 | 여러 곳에서 쓰나? | 쓰면 공통 폴더, 아니면 기능 폴더 안 |
| 관심사 | 같은 대상의 코드인가? | 한곳에 모으기 |
| 함께 변경 | 같이 바뀌는 파일인가? | 바로 옆에 두기 |
| 애매함 | 어디에 둘지 모호한가? | 팀 규칙 따르기 |
| 크기 | 파일 한두 개짜리인가? | 굳이 폴더로 나누지 않기 |

# 쇼핑몰 프로젝트 정리하기

## 리팩터링 전후 구조

### 전

```
src/
├─ apis/
│  └─ products.js
├─ components/
│  ├─ Content.jsx       ← "/" 경로의 홈 화면
│  ├─ Footer.jsx
│  ├─ Item.jsx
│  └─ Navbar.jsx
├─ contexts/
│  ├─ CartContext.js
│  └─ CartProvider.jsx
├─ pages/
│  ├─ AdminPage.jsx
│  ├─ CategoryPage.jsx  ← 목록 그리는 코드 중복
│  ├─ PricePage.jsx     ← 목록 그리는 코드 중복
│  └─ SortPage.jsx      ← 목록 그리는 코드 중복
├─ App.jsx
└─ main.jsx
```

### 후

```
src/
├─ apis/
│  └─ products.js
├─ components/
│  ├─ Footer.jsx
│  ├─ Item.jsx
│  ├─ ItemList.jsx      ← 새로 만듦 (상품 목록 그리기)
│  └─ Navbar.jsx
├─ contexts/
│  ├─ CartContext.js
│  └─ CartProvider.jsx
├─ pages/
│  ├─ AdminPage.jsx
│  ├─ CategoryPage.jsx  ← <ItemList /> 사용
│  ├─ HomePage.jsx      ← Content.jsx에서 이동 + 이름 변경
│  ├─ PricePage.jsx     ← <ItemList /> 사용
│  └─ SortPage.jsx      ← <ItemList /> 사용
├─ App.jsx
└─ main.jsx
```

## 1. Content.jsx → pages/HomePage.jsx (파일 역할)

### 변경 이유

- `Content`는 라우터의 `/` 경로에 연결된 화면 하나 전체인데, 여러 화면에서 쓰는 조각(Item, Navbar, Footer)과 함께 `components`에 들어 있었다.
- `components`는 여러 곳에서 쓰는 UI 조각, `pages`는 경로와 1:1로 연결되는 화면이라는 기준을 세우고 그에 맞게 옮겼다.
- 이름도 `Content`(내용)보다 역할이 드러나는 `HomePage`로 바꿨다.

### import 경로 수정

- `App.jsx`: `./components/Content` → `./pages/HomePage`
- `HomePage.jsx` 안의 `../apis/products`는 `components`와 `pages`가 같은 깊이라서 그대로 두었다.

## 2. ItemList 컴포넌트 분리 (중복 코드)

### 전

세 페이지에 같은 코드가 반복되었다.

```jsx
<div className="flex flex-col gap-3">
  <div className="flex justify-end">
    <button className="border-b border-black text-sm text-black">
      내 구매 내역
    </button>
  </div>
  <div className="flex flex-col gap-4">
    {items.map((item) => (
      <Item key={item.id} {...item} />
    ))}
  </div>
</div>
```

### 후

```jsx
// CategoryPage
{selected !== "" && <ItemList items={items} />}

// PricePage
{range !== null && (
  <ItemList items={items} emptyMessage="해당 가격대의 상품이 없어요." />
)}

// SortPage
<ItemList items={items} />
```

### 변경 이유

- 세 페이지는 보여 줄 상품을 고르는 방법(카테고리 filter, 가격 filter, sort)만 다르고, 목록을 그리는 방법은 같았다.
- 목록 디자인이나 "내 구매 내역" 버튼을 바꾸려면 세 파일을 모두 고쳐야 했다.
- 그리는 부분을 `ItemList`로 빼서 역할을 나눴다. 페이지는 "무엇을 보여 줄지", `ItemList`는 "어떻게 보여 줄지"를 맡는다.
- PricePage에만 있던 빈 목록 안내를 `emptyMessage` props로 받게 해서, 세 페이지 모두 상품이 없으면 안내 문구가 나오도록 맞췄다.

## 확인

- `pnpm lint` 에러 0개
- 홈 검색, 카테고리 필터, 가격 필터, 정렬, 장바구니 담기와 구매가 기존과 똑같이 동작하는 것을 확인했다.
