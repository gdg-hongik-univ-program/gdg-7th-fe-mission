컴포넌트 학습

React를 효율적으로 사용하기 위해서 사용하는 개념이자,
리액트 화면에서 UI 요소 구분할 때 사용되는 단위

쉽게 말해 리액트에서 앱을 이루는 가장 작은 '조각'이라 생각할 수 있다.

 비유 : 레고 블록으로 치면, 집을 쌓게 될 경우 하나의 블록이 컴포넌트가 된다.

컴포넌트를 사용하는 이유?

- 개발자들끼리 작업하는 범위가 겹치지 않게 하기 위해서

  - 만약 겹치면 비효율적으로 개발하게 되며, 사람 수가 많아질수록 더 힘들어진다.

어떤 기준으로 구분해야 하는가?

크게 5가지가 있다.

1. 재사용성 (Reusability)
	• 기준: 동일하거나 비슷한 UI/기능이 여러 곳에서 반복해서 쓰이는가?
	• 예시: 버튼(Button), 입력 필드(Input), 모달(Modal), 카드(Card) 등
	• 주의점: 무조건 재사용하겠다고 하드코딩된 로직을 억지로 묶으면 오히려 props가 복잡해지므로, 일반적이고 확장 가능할 때만 분리한다.

2. 단일 책임 원칙 (SRP, Single Responsibility Principle)
	• 기준: 하나의 컴포넌트는 ‘오직 한 가지 역할’만 수행하는가?
	• 예시: 피드 목록을 ‘불러오는 로직’과 ‘화면에 렌더링하는 UI’를 나누거나, 헤더·사이드바·푸터를 각각 독립된 컴포넌트로 분리한다.
	• 장점: 특정 기능이 변경될 때 수정해야 할 범위가 명확해진다.

3. 복잡성과 가독성 (Complexity & Readability)
	• 기준: 한 파일 안의 코드가 너무 길고 복잡해서 한눈에 읽기 어려운가?
	• 예시: 300~400줄이 넘어가는 하나의 컴포넌트 파일에서 특정 영역(예: 필터 섹션, 상세 테이블 등)을 별도 컴포넌트로 추출한다.
	• 장점: 코드 구조가 직관적이고 유지보수가 쉬워진다.

4. 비즈니스 로직과 UI의 분리
	• 기준: 데이터 처리, API 호출, 상태 계산 등의 로직이 UI 표현과 섞여 있는가?
	• 방법: 비즈니스 로직은 훅(Hook)이나 컨테이너/상위 컴포넌트로 분리하고, 하위 컴포넌트는 전달받은 데이터만 순수하게 그려주는 Presentational(UI) 컴포넌트 형태로 유지한다.

5. 렌더링 성능 (Performance)
	• 기준: 특정 상태(State)가 바뀔 때 관련 없는 무관한 UI까지 불필요하게 다시 그려지는가?
	• 방법: 독립적인 상태를 가진 작은 단위로 쪼개어 리렌더링 범위를 최소화한다.

대표적인 컴포넌트 : 클래스 컴포넌트

구성

1) Hooks
과거엔 함수형 컴포넌트가 state, 라이프사이클 지원하지 않았기에
클래스형 컴포넌트를 많이 사용했지만 React v16 이후부터
Hooks를 통한 state 및 LifeCycle 관리 가능해져
리액트에서 공식적으로 함수형 컴포넌트 사용을 권장👍
Hooks의 useState 사용해 state 관리할 수 있고
useEffect 사용해 LifeCycle 관리 가능🙆‍♀️

2) 직관적인 코드
Js 함수 선언, 화살표 함수 그대로 사용해
컴포넌트 사용 가능하기에 개발자에게 직관적👁‍🗨

3) 메모리 자원 효율
클래스형 컴포넌트에 비해 함수형 컴포넌트가 비교적 메모리 자원 적게 사용

제일 대표적인 컴포넌트 : 클래스 컴포넌트

JS의 "클래스" 기반 컴포넌트로,
class 정의하고 render( ) 함수에서 jsx 코드를 반환

1) class 키워드로 클래스 컴포넌트 생성

2) React.Component 상속
React의 ComponentClass 상속받아 Component 상속 필요

3) render( ) 메서드 필수로 사용
클래스 컴포넌트 안에 render( ) 메서드 꼭 필요하고 메서드 안에 JSX를 리턴🔁

4) this 키워드 사용하기
state, props, refs, 컴포넌트 메서드, 생명주기 메서드
사용할 때 this로 프로퍼티 참조하여 사용
